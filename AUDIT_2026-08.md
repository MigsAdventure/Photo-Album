## 00 — Where it stands

| Area | Status | Note |
|---|---|---|
| Guest upload path | **Solid** | Firebase resumable uploads, per-file progress, sensible compression |
| Bulk download | **Fragile** | Four routing tiers, one dead endpoint, one silent-failure path |
| Access control | **Absent** | No Firestore rules, no webhook auth, ownership is localStorage only |
| Secrets hygiene | **Breached** | RSA private key committed; 6,090 of 6,297 tracked files are node_modules |
| Interface | **Dated** | Works on mobile, but no albums, search, faces, or organizer console |
| Multi-tenancy | **Missing** | No concept of an agency, a client, or a reseller — required to sell it |

### The five things that matter

1. **Rotate and purge the committed SSH key**, and write Firestore security rules. Anyone can set any event to `planType: 'premium'` for free, and delete any guest's photos. (§03)
2. **Collapse the download pipeline from four tiers to one.** The frontend still routes 80 MB+ videos to a Google Cloud Run URL decommissioned in January 2025. (§02)
3. **Fix the zip streaming loop on EC2.** It opens every file's HTTP connection up front and lets them idle while the archiver drains them one at a time — the root cause of large-video failures. (§02)
4. **Don't move storage to GoHighLevel.** The 500 GB figure is from their WordPress hosting product, not the media library. (§01)
5. **Build the organizer console and the agency layer.** (§06)

## 01 — The GoHighLevel storage question

### What GoHighLevel actually offers (verified Aug 2026)

| Claim | Reality | Consequence |
|---|---|---|
| 500 GB storage | That figure belongs to HighLevel's **WordPress Hosting** "Truly Unlimited" plan. The Media Library is advertised as unlimited on paid plans. | "Unlimited" is fair-use marketing-asset storage, not a media backend. |
| Any file size | Hard caps: **25 MB** non-video, **500 MB** video. | 4K iPhone video regularly exceeds 500 MB. R2 is still required for exactly the files that hurt today. |
| API throughput | **100 requests / 10 seconds** per app per location; 200,000/day. | A 400-photo wedding is 400 upload calls — 40+ s of pure rate-limit budget, competing with CRM automations. |
| Access control | Media Library files are served from public URLs. No signed URLs, no per-object expiry, no per-event isolation. | Guest photos would be permanently world-readable and pooled into one shared library across every reseller client. |

Sources: [HighLevel media storage limits](https://gohighlevele.com/highlevel-support/media-storage-file-upload-limits/) · [Upload File into Media Storage — HighLevel API](https://marketplace.gohighlevel.com/docs/ghl/medias/upload-media-content/) · [HighLevel Support: Media Storage](https://help.gohighlevel.com/support/solutions/155000000259) · [WordPress Hosting changelog (source of the 500 GB figure)](https://ideas.gohighlevel.com/changelog/wordpress-hosting-more-storage-unmetered-bandwidth-for-all-plans)

### Recommendation

**Keep R2 as the storage plane. Move GoHighLevel up the stack, not down.**

R2 gives you what the media library can't: zero egress fees, signed URLs, lifecycle rules, per-event key prefixes, and multipart uploads for 2 GB videos. At $0.015/GB-month a 50 GB wedding costs **75¢/month** to store and nothing to serve. There is no meaningful cost saving to chase — but there is real risk in pooling every client's guest photos into one agency media library with public URLs.

### If you proceed anyway: the storage router

Stop calling storage SDKs directly from feature code. Replace with one interface and a policy:

- **Rule 1** — Video, or > 25 MB → R2 only (GoHighLevel cannot accept it)
- **Rule 2** — Event marked private → R2 only (public URLs unacceptable)
- **Rule 3** — Location quota healthy → GHL primary, R2 mirror, throttled to 8 req/s
- **Rule 4** — 429 or quota tripped → overflow to R2, flag event, keep going

Concretely: a `StorageProvider` interface (`put`, `getUrl`, `delete`, `stat`); an `R2Provider` (mostly extractable from `netlify/functions/r2-copy.js`); a `GHLProvider` wrapping `POST /medias/upload-file`; and a `StorageRouter` owning the rules plus a token-bucket limiter. Store the resolved provider and key on each photo document. Two non-negotiables: **always mirror to R2**, and **never route private events there**.

### GHL-1 — The existing GoHighLevel client is v1, browser-side, and leaks the API key · HIGH

```
src/services/ghlService.ts:4   GHL_API_BASE = 'https://rest.gohighlevel.com/v1'
src/services/ghlService.ts:13  this.apiKey = process.env.REACT_APP_GHL_API_KEY
```

Anything prefixed `REACT_APP_` is compiled into the bundle and readable by every visitor. If that key is ever populated, the entire GoHighLevel location is public. v1 is also superseded by the OAuth-based v2 API, where the media endpoints live.

**Fix:** delete the browser-side client. Move every call to a Netlify function using a server-only `GHL_ACCESS_TOKEN`; migrate to v2 with OAuth refresh. Confirm the key has never been deployed — if it has, rotate today.

### GHL-2 — The upgrade webhook grants premium to anyone who asks · CRITICAL

```
netlify/functions/ghl-webhook.js:32  if (webhookData.action === 'upgrade_confirmed')
```

No signature check, no shared secret, no verification that a payment occurred. A single `curl` with `{"action":"upgrade_confirmed","eventId":"..."}` flips any event to unlimited. Event IDs are partially guessable (`2026-06-14_smith-wedding_a1b2c3d4`). The handler also logs the full request object including headers, so any token added later lands in plaintext logs.

**Fix:** require an HMAC signature verified against a server-side secret, reject requests older than five minutes, and confirm the payment through the GoHighLevel API before writing `planType`. Remove the `JSON.stringify(event)` header dump.

## 02 — Large files & the zip pipeline

Sixteen markdown files describe fixes to this subsystem. The individual fixes were mostly correct; nothing was ever removed, so a request can traverse four independent routers each with its own thresholds, rate limiter, and fallback.

### The route a 90 MB video takes right now

1. **Browser** — `photoService.ts:380`, "video over 80 MB" rule fires
2. **Google Cloud Run** — decommissioned Jan 2025; burns the full 30 s timeout, then falls back
3. **Netlify** — `email-download.js:475`, different threshold (50 MB), re-routes
4. **CF Worker** — `index.js:166`, third threshold (80 MB), re-routes
5. **Lambda → SQS → EC2** — where the work finally happens

Every hop can rate-limit, time out, or fall into a different branch. The user watches a spinner for 30 seconds before any real work begins.

### ZIP-1 — Frontend routes large videos to a service removed 19 months ago · CRITICAL

```
src/services/photoService.ts:421  const CLOUD_RUN_URL = 'https://wedding-photo-processor-767610841427.us-west1.run.app'
```

`project-state.md` records Google Cloud Run as "permanently removed, Jan 20 2025." The frontend never got the memo. Any collection with an 80 MB+ video, over 500 MB total, or more than 10 videos hits this URL first and waits out `AbortSignal.timeout(30000)`.

**Fix:** delete `routeToGoogleCloudRun` and the client-side analysis block (lines 327–403). The browser should POST `{eventId, email}` to one endpoint and let the server decide — which also closes a hole where a client can hand-craft the `photos` array sent to the processor.

### ZIP-2 — The Netlify fallback path can never finish · CRITICAL

```
netlify/functions/email-download.js:507  processLargeCollectionInBackground(...);   // no await
netlify/functions/email-download.js:509  return { statusCode: 200, ... }
```

The function kicks off an async job, returns, and Netlify freezes the container the moment the response is sent. Real background work on Netlify requires a filename ending in `-background`; none of the fifteen functions in that directory do. Whenever the Cloudflare Worker is unreachable, the user is told "you'll receive an email in 3–8 minutes" and receives nothing — no email, no error, no log line.

Even if it ran, it couldn't: the code accumulates `zipChunks` and calls `Buffer.concat` (line 623), holding the whole archive in memory inside a function capped at 1 GB and 26 s.

**Fix:** delete this path. With the pipeline collapsed (ZIP-4), Netlify validates and enqueues. One reliable worker beats three unreliable fallbacks.

### ZIP-3 — The EC2 streaming loop holds every download connection open at once · CRITICAL

```
aws-ec2-spot/wedding-photo-processor-streaming-fixed.js:401  const response = await fetch(photo.url, {...});
aws-ec2-spot/wedding-photo-processor-streaming-fixed.js:415  archive.append(nodeStream, { name: photo.fileName });
```

**This is the root cause of the large-video failures.** The loop fetches file 1, appends its live response stream to the archiver, and immediately moves to file 2 — but `archiver` processes entries strictly in order, one at a time. With 30 files you end up with 30 open Firebase HTTPS connections, 29 idling while the first is compressed and uploaded.

Google Cloud Storage closes idle connections. A 400 MB video 25th in the queue may wait minutes before the archiver reaches it, by which point the connection is dead — the entry silently truncates or the job errors mid-archive. It degrades exactly in proportion to file size and count.

Two supporting defects in the same function: the 2-minute per-file `AbortController` (line 399) is armed at fetch time rather than consumption time, so it fires on slow-queue files that were downloading fine; and `uploadPromise` is referenced inside `archive.on('end')` at line 319 but declared with `const` at line 386 — it works only because the event happens to fire later.

**Fix:** make the loop strictly sequential — append one entry, wait for archiver's `entry` event for that file, then fetch the next. Move the timeout to wrap the whole append-and-drain cycle. Add a per-file retry that re-issues the fetch on a dead socket. Hoist `uploadPromise` above the handler that awaits it.

### ZIP-4 — Four routers with four different size thresholds · HIGH

```
photoService.ts:380              80 MB video / 500 MB total / 10 videos → Cloud Run
email-download.js:462            50 MB total → Cloudflare Worker
cloudflare-worker/index.js:166   80 MB any file or total → AWS
lambda-function.js               no threshold — always launches EC2
```

These disagree, so identical collections take different paths depending on entry point. A 60 MB photo-only collection is "large" to Netlify and "small" to the Worker, so it ping-pongs. Four copies of the routing logic is also why the Cloud Run reference survived — it was removed from three of them.

**Fix:** one entry point, one threshold table. `POST /api/downloads` → validate → enqueue to SQS → EC2 archives everything regardless of size. Small collections finish in seconds anyway.

### ZIP-5 — Job timeout exceeds SQS visibility timeout — the duplicate-email bug · HIGH

```
wedding-photo-processor-streaming-fixed.js:212  VisibilityTimeout: 900        // 15 minutes
wedding-photo-processor-streaming-fixed.js:231  const timeoutMs = Math.max(600000, totalSize / 100);
```

For a 5 GB collection `totalSize / 100` = 50,000,000 ms — just under 14 hours. SQS makes the message visible again after 15 minutes, so a second consumer picks up the same job while the first is still working. Both finish. Both send email. Commit `88c6592` describes exactly this.

**Fix:** extend visibility continuously with `ChangeMessageVisibility` on a heartbeat, cap the job timeout well below the maximum, add a DLQ after two attempts. Write a `downloadJobs` record keyed by event so a repeat request within a few minutes returns the existing link.

### ZIP-6 — Every archive for an event writes to the same R2 key · HIGH

```
wedding-photo-processor-streaming-fixed.js:272  const zipKey = `events/${eventId}/photos.zip`;
```

A fixed key means a second request overwrites the object while a guest may be mid-download — they get a corrupt file. Every previously sent email link silently changes content. The Netlify path meanwhile writes to `downloads/event_${eventId}_photos_${Date.now()}.zip` (line 807), an unrelated namespace.

**Fix:** one scheme everywhere — `archives/{eventId}/{jobId}.zip` — with an R2 lifecycle rule expiring archives after 30 days.

### ZIP-7 — Failed files are counted but the job still reports success · MEDIUM

```
wedding-photo-processor-streaming-fixed.js:409  failedCount++; continue;
```

If 40 of 200 files fail, the archive is built from 160 and the email looks normal. `failedCount` is passed to `sendEmail` but `direct-email.js` doesn't accept the parameter, so it's dropped.

**Fix:** retry each failure twice against a refreshed URL. Name any still-missing files in the email with a one-click retry. Above a 5% failure rate, alert yourself instead of sending a success email.

### ZIP-8 — An orphaned job can sit in the queue with nothing to consume it · MEDIUM

```
aws-ec2-spot/lambda-function.js:102                          filters on instance-state 'running' | 'pending'
wedding-photo-processor-streaming-fixed.js:64                IDLE_TIMEOUT = 5 minutes
```

The launcher sees a running instance and returns "existing instance will process." If that instance was seconds from its idle timeout it terminates, and nothing ever polls the message. No watchdog, no DLQ — the request disappears.

**Fix:** have the processor drain the queue to empty before considering itself idle; add a CloudWatch alarm on `ApproximateAgeOfOldestMessage` that re-triggers the launcher. Better: replace instance-lifecycle guesswork with a container service that scales from zero on queue depth.

### ZIP-9 — The rate limiters and circuit breakers don't do anything · MEDIUM

```
email-download.js:16   const GLOBAL_REQUEST_TRACKING = new Map();
email-download.js:267  const requestId = Math.random().toString(36).substr(2, 9);
email-download.js:406  checkCircuitBreaker(requestId);
```

Roughly 250 lines across two files. The tracking Maps are per-instance: Netlify spins up fresh containers and Cloudflare runs a separate isolate per edge location, so each limiter sees a fraction of traffic and forgets everything on cold start. And the circuit breaker keys on a `requestId` generated fresh inside the same handler — `tracking.attempts` is always 0, so it can never open.

**Fix:** delete both. Replace with one durable counter (Firestore doc or Cloudflare KV) keyed by `{eventId}:{email}`, enforced at the single entry point from ZIP-4.

### ZIP-10 — The R2 copy buffers whole files in a Netlify function · MEDIUM

```
netlify/functions/r2-copy.js:92  const buffer = await response.buffer();
```

Every upload triggers this, pulling the file entirely into memory before writing to R2. A 1.5 GB video — which `videoService.ts:39` explicitly permits — exceeds the memory limit and the execution window. Those files never reach R2, so the gallery serves them from Firebase at $0.12/GB egress and the zip worker downloads them from Firebase too, feeding straight into ZIP-3.

**Fix:** stop copying. Upload directly to R2 from the browser via presigned multipart URL, and drop Firebase Storage from the write path — it currently costs double storage and full egress for no benefit. Firestore stays as the metadata store.

## 03 — Security & data integrity

### SEC-1 — An RSA private key is committed to the repository · CRITICAL

```
aws-ec2-spot/wedding-photo-spot-key.pem   (tracked in git, present in history)
```

The SSH key for your EC2 processing instances, in the working tree and every clone. If the repo is or becomes public — or any collaborator's laptop is compromised — it grants shell access to instances holding R2 credentials, SQS access, and the ability to launch further instances on your account.

**Fix:** treat as compromised. New key pair, update the launch template, delete the old key from EC2, purge from history with `git filter-repo`, force-push, add `*.pem` to `.gitignore`. Then rotate the R2 and AWS credentials that instance could reach.

### SEC-2 — No Firestore security rules exist in the repository · CRITICAL

Storage rules are version-controlled; Firestore rules are not, which strongly suggests they were never written. Every write goes directly from browser to Firestore. Without rules, all of the following work from the console of any event page:

- `updateDoc(eventRef, {planType: 'premium', photoLimit: -1})` — free unlimited uploads. The function that does this (`photoService.ts:594`) is already exported client-side.
- `deleteDoc` on any photo in any event — the ownership check at `photoService.ts:613` reads `localStorage`, so it's advisory only.
- Reading and enumerating every event and photo across all clients.
- Editing `organizerEmail` on someone else's event, then requesting their gallery by email.

**Fix:** commit a `firestore.rules` making `planType`, `photoLimit`, `paymentId`, `photoCount` writable only by the Admin SDK; allow photo creation only with a matching `uploadedBy`; permit deletes only through a server function. Move upgrades and count increments into Netlify functions. Ship rules in the repo with an emulator test.

### SEC-3 — The EC2 launcher is a public URL with no authentication · HIGH

```
cloudflare-worker/wrangler.toml:9  AWS_LAMBDA_URL = "https://szfs7ixxp34s6nbeonngs726om0ihnqx.lambda-url.us-east-1.on.aws/"
```

Committed in three files and present in the deployed Worker. Anyone who POSTs `{eventId, email, photos}` queues a job and launches an EC2 instance on your account. No signature, no allowlist, no cap — a billable denial-of-wallet endpoint that will also send email from your domain to any address the caller supplies.

**Fix:** switch the Function URL to `AWS_IAM` auth and sign from the Worker with SigV4, or verify a shared secret header before doing any work. Cap concurrent instances. Never accept the recipient email from the caller — look it up from the event record.

### SEC-4 — Anyone can have any event's photos emailed to any address · HIGH

```
netlify/functions/email-download.js:309  const { eventId, email } = parsedBody;
```

Both the event and the destination come from the request body and neither is verified. Event IDs are semi-guessable by construction, so a competitor or curious guest can exfiltrate an entire wedding gallery to an address they control. The archive URL is then a permanent unauthenticated public R2 link.

**Fix:** send only to the event's `organizerEmail`, or to an address that has verified ownership via magic link. Make the archive URL a time-limited signed R2 URL.

### SEC-5 — Photo deletion is enforced only in localStorage · HIGH

```
src/services/sessionService.ts:6   SESSION_STORAGE_KEY = 'wedding-app-session'
src/services/photoService.ts:613   canDeletePhoto → getPhotoOwnership(localStorage)
```

Ownership is a session ID the browser generates for itself. A user can edit it to any value. Storage rules explicitly block client deletes (`allow delete: if false`), so the Firestore document is removed while the file stays in Storage forever — the gallery shows it deleted, the bytes remain, and you keep paying.

**Fix:** route deletes through a server function that verifies the session and removes the Storage object, R2 object, and Firestore document as one unit. Give the organizer a moderation view.

### SEC-6 — Storage rules accept any upload that includes a sessionId field · MEDIUM

```
firebase-storage-rules.txt:12  allow create: if request.auth != null || request.resource.metadata.sessionId != null
```

Satisfied by `sessionId: "x"`. Combined with public event URLs, anyone can write unlimited files of any type into `events/{anyEventId}/` — including content served from your domain. No size cap, no content-type restriction.

**Fix:** constrain by `request.resource.size` and `contentType` at minimum. This disappears entirely with SEC-2 and ZIP-10.

### SEC-8 — `direct-email` is an unauthenticated phishing relay · CRITICAL

> **Added 2026-08-12 during Phase 1 implementation.** Not found in the original
> pass — I reviewed this file for correctness and did not ask who controls its
> inputs. Fixed in commit `f3d867f`.

```
netlify/functions/direct-email.js:42   const { email, downloadUrl, fileCount, finalSizeMB } = parsedBody;
netlify/functions/email-download.js:324  if (source === 'cloudflare-worker' && downloadUrl)
```

Both endpoints take a recipient address and a download URL from an
unauthenticated request body and render the URL into an anchor inside a
SharedMoments-branded "your photos are ready" email, sent from the authenticated
Mailgun domain. Anyone can deliver a convincing phishing message to any address,
pointing anywhere. Beyond the harm to recipients, sustained abuse gets the
sending domain blocklisted, which takes legitimate delivery down with it. The
template also fell back to `example.com` when `downloadUrl` was missing, so even
a malformed request produced a branded email.

**Fix (applied):** both require `INTERNAL_SERVICE_SECRET`, and the link must
resolve to the configured R2 host — so even a compromised internal caller cannot
put an arbitrary URL in front of a customer.

### SEC-9 — Live R2 credentials committed in seven files · CRITICAL

> **Added 2026-08-12 during Phase 1 implementation.** The original pass grepped
> for `AKIA` and `sk_live` prefixes but not for R2-style `KEY=value` assignments
> in shell and systemd files. Fixed in commit `f3d867f`; **rotation still
> required.**

```
aws-ec2-spot/lambda-function.js:298-299        Environment="R2_ACCESS_KEY_ID=06da59…"
aws-ec2-spot/user-data-al2023-auto-terminate.sh:513-514   (a second, different pair)
…and 5 more files
```

Two distinct Cloudflare R2 key pairs embedded as string literals, including in
the user-data the launcher bakes into every EC2 instance. They grant read, write
and delete on the production photo bucket — every customer's photos and every
generated archive — to anyone who has ever cloned this repository.

This is more urgent than SEC-1. The SSH key gave shell on an ephemeral
processing instance; these give direct control of the bucket the product lives
in.

**Fix (applied):** the launcher reads them from its own environment and throws
on a missing value rather than baking an empty credential into an instance that
would then fail every job with an opaque auth error. Literals replaced with
variable references in the six legacy user-data scripts.
**Still required:** rotation, per `docs/runbooks/credential-rotation.md`.

### SEC-7 — Deleted photos leave orphaned bytes in three places · MEDIUM

A photo exists as a Firestore document, a Firebase Storage object, and an R2 object. Deletion attempts the first two and never touches R2 (`photoService.ts:640–704`). Nothing reconciles them — a real problem the first time a guest asks you to delete their photo under a privacy request.

**Fix:** single server operation across all three stores, plus a nightly reconciliation job.

## 04 — Architecture & cost

| Component | Role today | Recommendation |
|---|---|---|
| Firebase Storage | Primary upload target, then copied to R2 | Drop from write path. $0.026/GB-month + $0.12/GB egress for a copy you already hold in R2. |
| Firestore | Events and photo metadata, live gallery | Keep — good fit. Add rules. |
| Cloudflare R2 | Display copy and archive destination | Promote to single storage plane. $0.015/GB-month, zero egress. |
| Netlify Functions | Upload proxy, R2 copy, email, GHL webhook, download router | Keep, narrowed to the API layer. Remove the 6 test functions from production. |
| Cloudflare Worker + Durable Object | Middle archiving tier | Remove. Duplicates the EC2 path, adds a hop with a 128 MB ceiling. |
| Lambda + SQS + EC2 Spot | Large archive processing | Keep the queue; replace instance-lifecycle scripting with a container that scales from zero. |
| Google Cloud Run | Referenced by the frontend; does not exist | Delete the reference. |
| Vercel config | `api/` routes and `vercel.json`, unused | Delete. Pins Node 18, duplicates the Netlify functions. |

### ARC-1 — Dependencies are 12–18 months stale, build tool discontinued · HIGH

```
package.json:42  "react-scripts": "5.0.1"
package.json:44  "typescript": "^4.9.5"
package.json:27  "aws-sdk": "^2.1692.0"     // v2 in maintenance mode
```

Create React App is unmaintained and its last release predates React 19, which you're on. Both AWS SDK v2 and v3 are installed, doubling the bundle. `node-fetch@2`, `multer`, `multiparty`, and `formidable` are all present for overlapping jobs.

**Fix:** migrate to Vite (typically half a day for a CRA app this size), TypeScript 5.x, drop `aws-sdk` v2 and the unused body parsers. Do this *before* the UI work in §05.

### ARC-2 — node_modules is committed — 6,090 of 6,297 tracked files · HIGH

Plus four built Lambda zip archives (~95k lines). Every clone is slow, every diff noisy, every dependency audit meaningless.

**Fix:** `.gitignore` `aws-ec2-spot/node_modules/` and `*.zip`, `git rm -r --cached`, build Lambda bundles in CI.

### ARC-3 — There is no test suite and no CI · MEDIUM

`src/App.test.tsx` is the CRA default. No `.github/workflows`. The 30+ ad-hoc `check-*.js` / `test-*.js` scripts in the root are debugging tools needing live credentials and a human reading output.

**Fix:** unit tests for the routing threshold table and storage router; Firestore rules tests against the emulator; one end-to-end test that uploads a small video and downloads the archive. Wire to a GitHub Action. Move the ad-hoc scripts to `scripts/`.

### ARC-4 — Twenty-six status documents in the root, several contradicting · MEDIUM

`DOWNLOAD_SOLUTION_COMPLETE.md`, `DOWNLOAD_FIXES_COMPLETE_SUMMARY.md`, `DOWNLOAD_FIX_COMPLETE_NETLIFY.md`, `SIMPLIFIED_DOWNLOAD_SOLUTION.md` and `BLOB_DOWNLOAD_SOLUTION_FINAL.md` describe the same subsystem at different moments. `project-state.md` lists the EC2 zip issues under "Do NOT Revisit" — which is how ZIP-3 survived. `README.md` is still the unmodified CRA template.

**Fix:** archive to `docs/history/`. Write one real `README.md` (setup, env vars, deployment, request flow) and one `ARCHITECTURE.md` describing what exists today. Delete the "do not revisit" list — it converts a fix into a permanent blind spot.

## 05 — Interface & experience

### UX-1 — The free plan allows two photos · CRITICAL

```
src/services/photoService.ts:250  photoLimit: 2
src/services/photoService.ts:272  photoLimit: data.planType === 'free' ? 2 : ...
```

The limit is per *event*, not per guest, so the third guest at a wedding is blocked and shown an upgrade modal for an event they don't own and can't pay for. From their side the app is broken. The organizer never finds out.

Commercially it's also the wrong shape — two photos isn't a trial, nobody experiences the product.

**Fix:** a time or capacity limit that lets the product demonstrate itself: unlimited uploads for 48 hours then view-only until upgrade, or a generous file count (150–250) with a soft warning at 80%. **Never block a guest** — a blocked guest is a lost photo you can never recover; an over-limit organizer is a sales conversation.

### UX-2 — There is no organizer console · HIGH

```
src/App.tsx:531  Routes: "/" (create), "/event/:eventId" (guest), 3 payment result pages
```

Creating an event returns a QR code and an email. After that there's no way to see your events, re-open one, check photo counts, moderate, download without the email round-trip, or invite a co-host. Lose the email and the event is effectively gone.

For a planner running six events a season this is the single biggest gap between what exists and what they'd pay for.

**Fix:** magic-link sign-in on the organizer email plus a `/dashboard`: event list with counts and storage used, per-event settings (title, cover, date, privacy, download permissions), moderation grid, direct download, QR/poster assets. ~2 weeks, and it's what turns the app into a subscription.

### UX-3 — The gallery loads every photo at full resolution · HIGH

```
src/components/EnhancedPhotoGallery.tsx:179  getMediaUrl → original file URL, no thumbnail variant
```

No thumbnail pipeline, no `srcset`, no lazy loading, no virtualization — `subscribeToPhotos` returns the entire collection and the grid renders all of it. A 400-photo wedding on a phone at the reception means several hundred MB over cellular before anything is usable.

Compounding it, `EnhancedPhotoGallery.tsx:156` runs `await canDeletePhoto(photo.id)` inside a loop over every photo on every snapshot — one Firestore read per photo per update, purely to decide whether to show a delete icon that localStorage already knows about.

**Fix:** generate 400px and 1200px WebP variants on upload (Cloudflare Images or a Worker on the R2 bucket), serve via `srcset`, lazy-load below the fold, paginate the subscription to 60. Read ownership from the local session list. Expect tens of seconds → under two.

### UX-4 — Download requires an email round-trip even for one photo · HIGH

A guest who wants one great picture of themselves must type an email, wait minutes, switch to their inbox, download an archive of the entire event, and extract it on a phone. The email even says: "You may need a file manager app to extract the photos."

**Fix:** direct download for single files and small selections — R2 with `Content-Disposition` handles it instantly, and the code already exists in `media-download.js`. Add multi-select. Reserve email for genuinely large archives and show live progress on the page.

### UX-5 — Uploads are strictly sequential and don't survive a locked screen · MEDIUM

```
src/components/BottomNavbar.tsx:250  startUploads → for (let i = 0; i < queue.length; i++) { await ... }
```

Thirty phone photos upload one at a time. A service worker and a background upload service exist in the codebase but the navbar path doesn't use them — lock the phone mid-upload and the queue stops with no resume.

**Fix:** three concurrent uploads, queue persisted to IndexedDB, resume on return, wire in the existing service worker. One aggregate progress bar rather than a list of thirty.

### UX-6 — The gallery is a single undifferentiated grid · MEDIUM

No albums, chronological grouping, photo/video filter, search, favorites, sort, or any way to find yourself in 400 pictures. Every event looks identical — same pink-to-purple header — which undercuts the premium tier and makes white-labeling impossible.

**Fix:** group by time-of-day segments derived from timestamps ("Ceremony", "Reception"), add photo/video filter and favorites, let the organizer set a cover image and accent color. `EventBranding` already exists in `types.ts:49` and is never used.

### UX-7 — Interface polish gaps · MEDIUM

- `App.tsx:148` and `:90` use `alert()` for errors — jarring, unstyled, blocking.
- `App.tsx:454–509` builds a success toast by injecting raw DOM and a `<style>` tag from inside a React effect.
- No dark mode, despite a theme system being one `createTheme` call away.
- Nothing is translated; guest-facing copy is English-only.
- No accessibility pass — the lightbox doesn't trap focus, photos have no meaningful alt text.
- Empty states are bare. A guest opening an event with no photos yet is the highest-intent moment in the product, and it shows an empty grid.

## 06 — Building the resellable product

### The missing data model

Everything hangs off a single `events` collection with an organizer email string. To resell you need three levels: **Agency** (you or a reseller — branding, domain, plan) → **Organizer** (planner or photographer — many events) → **Event** (photos and guests). Adding this later is a painful migration; adding it before you have paying resellers is a day of schema work.

### What each buyer needs

| Buyer | What sells them | Build |
|---|---|---|
| Wedding planners | Running many events without touching each one; the gallery carrying their brand | Multi-event dashboard, white-label subdomain and logo, per-event templates, client handoff link |
| Photographers | Guest photos complement their work rather than compete; plus lead capture | Pro gallery upload for their edited set, watermarking, "book me" CTA, guest email capture |
| Venues | A permanent QR at the venue that works for every event held there | Reusable venue codes that spawn a fresh event per booking, venue-branded landing |
| Party hosts (self-serve) | Under two minutes from landing page to a QR code on the table | Frictionless create flow, printable table-tent PDF, one clear price |
| Corporate | Control and cleanup | Pre-moderation queue, expiry policy, export, invoice billing |

### Where AI earns its place

Four features that map to a specific complaint a planner would actually make:

- **Find me.** On-device face grouping, opt-in: a guest takes one selfie and sees only photos containing them. The most-requested feature in event galleries; it removes the "scroll 400 photos" problem and makes single-photo download (UX-4) the primary action.
- **Automatic culling.** Detect blurred, duplicate, and eyes-closed shots and collapse them into a "more like this" stack. 400 photos becomes a curated 180, and the storage bill drops.
- **The highlight reel.** Best 30–60 photos cut into a 60-second video set to music, emailed the morning after. This is what a couple posts to Instagram — your best acquisition channel and an obvious premium upsell.
- **Auto-captioning and alt text.** Searchable descriptions ("cake cutting", "dance floor") give you gallery search for free and fix the accessibility gap in UX-7.

All four run on upload, off the critical path, requiring nothing from the guest. Run them as a queue consumer alongside the archive worker.

### Where GoHighLevel genuinely belongs

- **Every guest who uploads is a lead.** With consent, push them into the organizer's GoHighLevel location as a contact tagged with the event — for a photographer or venue that's worth more than the storage.
- **Payments and upgrades** through GoHighLevel order forms rather than the current unverified webhook (GHL-2), with plan state written back by a signed callback.
- **Lifecycle automations:** event created → reminder 3 days before → "your gallery is live" the morning after → highlight reel → "archives expire in 7 days" → anniversary re-engagement. Native GoHighLevel workflow territory; none of it exists today.
- **Reseller onboarding as a snapshot:** planner buys → location provisioned → subdomain and branding configured → whole funnel templated.

### Pricing shape

The current model — one $29 upgrade per event, unlocked after two photos — leaves recurring revenue on the table. A structure fitting the three buyers: a free tier genuinely usable for a small party (capped by time, not two photos); a per-event tier around $39–79 for one-off hosts; and an agency subscription at $99–249/month covering unlimited events, white-labeling, and GoHighLevel lead sync. **The agency tier is the business — the per-event tier is the demo that sells it.**

Phases 1 and 2 are sequential — don't restructure the pipeline while credentials are still exposed. Phases 3–5 can overlap. Phase 6 shouldn't start until the organizer dashboard exists, because every feature in it needs a surface to be configured from.

---

Two things worth saying plainly. First, the engineering instinct throughout this codebase has been to add a fallback when something failed, and each fallback was individually reasonable. The compounding cost is four routers and an inability to reason about any single request — almost all of phase 2 is deletion. Second, the app is genuinely close: guest upload works, the gallery works, the QR flow works. What separates it from something you can put in front of a planner is a dashboard, a limit that doesn't punish guests, and a download that doesn't go through email. That's weeks, not months.
